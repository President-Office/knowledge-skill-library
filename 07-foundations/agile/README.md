# 敏捷与迭代式交付

## 核心定位

敏捷是一种在需求和方案存在不确定性时，通过短反馈周期持续交付价值、检验假设并调整方向的工作方式。它不是某套会议、看板或角色的同义词；Scrum、Kanban 和 XP 是可以按场景选择和组合的实践框架。

敏捷也不等于不做计划、不写文档或不重视设计。计划和文档应服务于协作、决策与验证，并随着新证据更新，而不是成为脱离实际的审批产物。

敏捷价值观强调人与协作、可工作的成果、客户合作和响应变化；流程、文档、合同和计划仍然有用，但不能凌驾于前述目标之上。是否敏捷应看团队能否持续学习和交付，而不是是否完成一套仪式。

## 为什么重要

软件项目的风险通常不只是实现困难，还包括：

- 实际用户问题与最初理解不一致；
- 需求、依赖和约束在交付过程中发生变化；
- 大批量交付让错误和误解到很晚才暴露；
- 开发完成后才发现产品没人使用，或运维成本无法接受。

小批量交付和频繁反馈能缩短发现这些问题的时间，让团队在投入继续扩大之前修正方向。

## 关键工作机制

1. **围绕结果**：明确目标用户、待解决的问题和预期业务/用户结果。
2. **拆小工作**：将工作切成可独立验收、尽早反馈的增量，控制并行数量。
3. **建立完成定义**：事先约定测试、审查、文档、发布和运行要求，避免“代码写完”被误认为“已交付”。
4. **尽早验证**：通过真实用户反馈、可运行的软件、自动化测试和可观察指标检验假设。
5. **定期调整**：根据证据更新优先级、范围和方案；记录重要决策及其依据。
6. **持续改善**：复盘阻塞、缺陷、等待和返工，选择少量具体改进并验证效果。

## 常见框架的侧重点

| 方法 | 主要关注 | 适用提示 |
| --- | --- | --- |
| Scrum | 短期固定长度的 Sprint、共同目标与经验主义检查 | 工作适合按迭代聚焦，团队能稳定评审和复盘时 |
| Kanban | 显式工作流、限制在制品（WIP）、管理流动和持续改进 | 工作持续到达、优先级变化频繁或需要改善交付流时 |
| XP | 小步发布、持续集成、测试驱动、重构和结对等工程实践 | 需要加强工程反馈并保持代码可变更时 |

框架是实现反馈和协作的手段，不应为了形式完整而增加不必要的角色、会议或工件。根据团队规模、风险和工作类型选择最小够用的机制。

### Scrum 的最小结构

采用 Scrum 时，不要只保留 Sprint 名称和每日站会。其核心结构包括：

- **责任**：Product Owner 关注产品价值与 Product Backlog；Scrum Master 帮助团队理解并改进 Scrum；Developers 负责每个 Sprint 形成可用的 Increment。
- **事件**：Sprint、Sprint Planning、Daily Scrum、Sprint Review、Sprint Retrospective，各自服务于计划、检查成果或改进。
- **工件与承诺**：Product Backlog 对应 Product Goal；Sprint Backlog 对应 Sprint Goal；Increment 对应 Definition of Done。

团队若不采用完整 Scrum，也应保留清楚的目标、优先级、完成定义和反馈责任，不要混用术语却丢失这些机制。

### 小团队的轻量起步方式

对个人或小团队，可以从待办清单、明确优先级、限制同时进行的工作、每周查看可运行成果和用户反馈、定期复盘阻塞开始。是否设置固定 Sprint 或会议，由协作和反馈需要决定；异步更新通常可替代不必要的状态会议。

## 度量与反模式

优先观察用户/业务结果、前置时间（Lead Time）、周期时间（Cycle Time）、吞吐量、在制品（WIP）、缺陷逃逸、返工、发布失败和运行质量。度量用于发现系统问题和改善决策，不应用单一数字给个人排名；不同团队的速度/故事点也不应直接横向比较。

常见反模式：

- 只按完成的故事点、任务数或代码行数衡量价值；
- 把每日站会、迭代仪式或看板更新当成交付成果；
- 迭代结束才集成、测试或让用户看到产品；
- 为了每次都“按计划完成”而隐藏风险或降低质量；
- 持续增加需求，却不重新评估容量、成本和优先级；
- 把敏捷误解成不需要架构、测试、文档或长期维护。

## 与相邻方法的边界

- **敏捷**是价值取向和一组适应变化的原则，不是一套固定流程。
- **Scrum、Kanban、XP**是不同的工作管理或工程实践，可选用、组合，但应知道各自解决什么问题。
- **DevOps / 持续交付**关注开发与运行反馈、自动化和安全发布；它能支撑敏捷交付，但不等同于 Agile。
- **瀑布式或阶段式治理**在需求稳定、监管或高风险场景仍可能合适；也可以在阶段门内采用短周期验证。方法选择应服从风险、可逆性和反馈条件。

## AI 时代的敏捷

AI 可以缩短实现时间，但不能自动证明需求正确、代码可靠或产品有价值。生成更快也可能让项目启动过多、审查与集成积压、维护面扩大。因此：

- 用短周期验证问题和用户价值，不把原型直接当生产级产品；
- 记录模型/API、人工审查、返工、测试、部署和维护的全生命周期成本；
- 设定每阶段的时间/费用上限、成功指标和停止条件；
- 按风险安排人工审查、自动化测试、审批和回滚；
- 用释放出来的时间加强反馈、验证和简化，而不是无条件扩大范围。

敏捷的关键收益是尽早学习和减少错误投入；AI 的速度应帮助团队更快取得证据，而非更快累积未经验证的工作。

通用敏捷原则维护在本共享知识库；AI 特有的 Agent 协作、AI Coding 工具和 AI 项目交付流程，应在对应 AI 知识库维护，避免两处复制后逐渐不一致。
