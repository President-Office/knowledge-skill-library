# 软件工程

## 核心定位

软件工程是以有纪律、可验证和可持续的方式，开发、交付、运行和演进软件的实践。它关注的不只是代码实现，还包括需求、协作、质量、风险、运行环境和维护成本。

计算机科学解释计算与程序的基础；软件工程则组织人、流程和技术，把这些基础转化为可靠的软件产品。学习路线见 [[07-foundations/computer-science/README]]。

## 软件生命周期

| 环节 | 关键问题 | 常见产物或证据 |
| --- | --- | --- |
| 发现与需求 | 谁遇到什么问题，什么结果才有价值？ | 目标用户、问题陈述、范围、验收标准 |
| 设计 | 约束、数据、接口、模块和风险是什么？ | 架构与数据模型、接口契约、决策记录 |
| 实现 | 如何以清楚的职责和边界改变系统？ | 代码、配置、迁移、可审查的变更 |
| 验证 | 如何证明行为满足需求并保护已有能力？ | 自动化测试、静态检查、审查结果 |
| 发布 | 如何安全地把变更交给用户？ | 版本、变更说明、部署与回滚方案 |
| 运行 | 如何知道系统健康，如何处理故障？ | 日志、指标、追踪、告警、操作手册 |
| 演进 | 如何控制变化、兼容性和技术债？ | 用户反馈、维护计划、重构和退役决策 |

这些活动通常循环交织，不必被理解为一次性、只能顺序执行的瀑布阶段；但每次变更都应覆盖与风险相称的需求、设计、验证和运行考虑。

## 质量属性

除了功能正确性，软件通常还需要权衡：

- **可维护性**：未来的人能否安全理解和修改？
- **可靠性**：故障、超时或部分失败时能否保持可接受行为？
- **安全性**：权限、数据和外部输入是否受到适当保护？
- **性能与成本**：延迟、吞吐、资源和费用是否满足目标？
- **可观察性**：能否用证据判断系统发生了什么？
- **兼容性与可移植性**：升级和迁移是否有清晰边界？

质量不是某个单独角色在最后阶段“负责”的事；它应从需求和架构开始，并由测试、审查和运行反馈共同验证。

## 工程控制机制

- 使用版本控制和小型、可审查的变更。
- 通过自动化测试和持续集成尽早发现回归。
- 在接口和数据边界验证输入、不变量、权限和错误路径。
- 记录重要决策及依据，避免依赖隐含上下文。
- 部署前准备健康检查、监控和回滚路径。
- 用 [[07-foundations/design-principles/measure-first]] 支持性能和复杂度决策。
- 以 [[07-foundations/agile/README]] 缩短交付与用户反馈周期。

具体实现应结合 [[07-foundations/README]] 中的 SOLID、KISS、YAGNI、Fail Fast、最小权限等原则，不将原则机械化为额外层次或仪式。

## AI 时代的全生命周期成本

AI 能降低部分实现和资料整理的时间，但一个项目的成本还包括：

- 模型/API 和第三方服务；
- 需求澄清、代码审查、测试、集成和返工；
- 数据准备、部署、监控、故障响应和安全治理；
- 用户支持、升级兼容和长期维护；
- 因项目过多产生的切换、协调和维护负担。

因此，代码生成速度或单次 API 费用都不足以代表项目经济性。应按可验证的用户/业务结果评估总投入，设置小范围试点的时间与费用上限、成功指标和停止条件。模型输出仍需按风险进行测试和人工检查。

### 可操作的复盘问题

- 用户是否实际使用并获得了预期结果？
- 质量、可靠性和安全是否达到验收要求？
- 模型/API 与人工审查、返工、运维和维护的总成本是多少？
- 哪些成本随着项目规模或使用量增长？
- 继续、调整、扩展或停止，分别依据什么证据？
